# Explicit PR context adversarial review

Review date: 2026-09-09. This records local implementation review, not production validation. The producer reviewer independently inspected the backend, migration, worker, and dashboard changes in the same worktree. The end-to-end reviewer independently challenged the producer contract.

## Findings and resolutions

- **P1 — Old worker rollback with queued sidecars needs a gate.** `PostgresTelemetryQueue.claimMatching` does not filter by supported normalizer version. The new migration enqueues collector batches with `sherlock.pr-context.v1`, which an older worker cannot normalize. Schema compatibility for native traffic does not imply compatibility with new context jobs. Stop new producer traffic, prevent further context ingestion, and drain context jobs with a compatible worker before rolling back to an old worker. If draining fails, retain the compatible worker with verification disabled. Preserve raw/audit data and avoid exhausting job retries through repeated incompatible claims. The deployment plan must verify this gate against actual pending and leased jobs; this finding is based on code inspection.
- **P2 — Producer/server PR number bounds diverged.** The producer initially accepted JavaScript-safe integers while the server stores PostgreSQL `integer`. A locally accepted value above 2147483647 would be rejected on upload. The producer and contract now use the server's signed 32-bit range; an overflow rejection test covers it. Found by the independent end-to-end reviewer.
- **P2 — Filename alone is insufficient provider evidence.** The general Claude discovery helper permits identity-free prefixes. Reusing that permissiveness for explicit linking could accept a renamed Codex JSONL file as a Claude session if its filename matched. Explicit linking now additionally requires a matching native Claude session/agent declaration in the bounded prefix. The native-validation test includes a Codex file renamed to the requested Claude UUID filename. Missing files remain an explicitly labeled manual declaration; they do not imply a provider-native check.

## Checked trust and consistency boundaries

Code inspection confirms that collector sidecars return no activity events, no session projection, and no SCM projection. Their append-only facts retain native source-record provenance. Event deduplication includes provider, exact native session, operation, target, and canonical timestamp in the semantic hash; same event ID with conflicting semantics invalidates the visible association. Local producer tests check stable raw bytes across offline retries and acknowledgement.

The dashboard matches workspace, collector, person, exact native session, and provider role, checks for legacy mixed-provider event history, and applies the supplied MVCC snapshot to links, conflicts, retractions, and verification observations. Retractions only affect matching scope and referenced link events. Provider collision checks and the migration trigger retain the legacy session uniqueness key while refusing a cross-provider update; they do not invent another session or quietly assign a colliding native record.

The GitHub worker checks a configured workspace/repository allowlist before constructing a fixed direct GitHub PR API endpoint. It disables redirects, validates the returned base repository and PR number, and persists only identity/state observations, not broad private repository metadata. Once checked, immutable repository and PR IDs are passed back on rechecks to prevent silently accepting a reused repository name. A rename redirect fails closed as an identity mismatch; automatic rename migration is outside v1. The UI distinguishes commit associations from collector-reported explicit context and labels pending/unavailable checks without presenting them as verified links.

These checks do not authenticate the uploader/person/session relationship. The existing public collector grant uses declared identity, and GitHub access proves neither authorship nor that every activity record belongs to a linked PR. A malicious party able to impersonate the collector remains inside that known trust limitation.

## Local evidence

`PYTHONPATH=packages/telemetry-collector/src python3 -m unittest discover -s tests/collector` passed 146 tests. The focused PR-context module passed 14 tests after the stricter provider-prefix check. Covered scenarios include both providers, successful/failed creation integration, explicit manual CLI selection, multiple PRs and simultaneous sessions, retractions arriving first, duplicate/replayed/conflicting events, concurrency, offline retry, immutable bytes, native identity mismatches, subagent identity without inheritance, and collector/destination binding.

This review does not substitute for the committed real collector-to-Storage/Postgres-to-worker-to-dashboard end-to-end harness, CI, production read-only checks, or an authorized production canary. Their results and limitations belong in the implementation PR and coordinated rollout plan.

## Fresh independent review — 2026-09-09

The fresh reviewer inspected the uncommitted producer, contracts, ingestion, normalization, migration, worker verification/selection, dashboard projection, and acceptance harness. No production mutation or concurrent database test was performed by this reviewer.

- **P1 — Offline delivery could relabel queued context after configuration drift.** The original implementation checked the retained sidecar binding only during enqueue. Every ordinary drain constructed an HTTP envelope from the current configuration. A no-network reproduction queued a sidecar as synthetic collector A and intercepted a drain preparing that same native-session declaration with synthetic collector B's email, installation ID and endpoint. The fix persists the binding in durable spool metadata and verifies it centrally in `HttpTransport` before any request. Both explicit and background drains retain mismatched records for retry with the original configuration; native spool behavior remains unchanged. Tests cover email, installation and destination drift, transient offline requeue, ordinary CLI drain, original-configuration recovery, unchanged raw bytes and no attempted network request on mismatch. This prevents accidental relabeling; it does not authenticate a malicious uploader.
- **P2 — Creation could perform a known-unlinkable external operation.** Destination mismatch was discovered only after `gh pr create` succeeded. The creation guard now checks the local binding before GitHub creation and serializes creation/replay checks through enqueue. Tests establish no CLI invocation on configuration mismatch and one invocation for concurrent creation with the same event ID. Remote creation and local persistence remain non-atomic; after an interrupted remote operation the documented manual link recovery still applies.
- **P2 — A response bound could remove all activity evidence.** The initial dashboard projection threw on the 51st valid distinct link even though ingestion permitted it, causing the interval containing that session to fail. Bounded output now includes an explicit truncation indicator and UI notice, preserving unrelated activity/prompt evidence. A 51-link regression passes.
- **Acceptance gap — SHA association A versus explicit context B.** The initial end-to-end fixture merely supplied a starting SHA; it did not create a legacy commit association or assert its coexistence. The expanded real HTTP/Storage/Postgres/worker/dashboard workflow now synchronizes a separate SHA-derived PR #81 association and asserts it alongside explicit #91/#92/#95 context. That workflow passed locally; its GitHub failure/lifecycle responses are controlled at the external API boundary.

After the delivery-binding fix, the full collector suite passed 148 tests. An additional concurrent-creation regression brought the focused context module to 17 passing tests. These are local results, and this review makes no claim of production behavior or live GitHub mutation coverage.

- **P2 — Undocumented multi-event sidecars could invert transaction lock order.** Two batches containing the same event IDs in opposite order could each hold one advisory lock while waiting for the other. V1 already specifies one event per immutable sidecar, so both Python manifest validation and server sidecar validation now require exactly one record. The server regression supplies a correctly hashed/compressed two-record payload and verifies rejection before a committed receipt. This bounds fact insertion to one declaration lock without changing append-only schema or native batch handling. The focused suites passed 17 Python collector tests and 8 Deno sidecar tests using CI-pinned Deno 2.5.1; the edited Deno files were formatted.
